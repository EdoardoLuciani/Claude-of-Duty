# M4 authoring: source first

Edit Python, then regenerate the whole weapon. The generated M4 `.blend`, GLB,
PNG maps and manifest are not authoring inputs. Never repair exported GLB bytes,
load a previous M4 blend as a build fallback, or retune materials in the loader.
Normal Vite builds use the committed GLB and do not require Blender.

## Editing map

| Concern                                                                          | Source                                        |
| -------------------------------------------------------------------------------- | --------------------------------------------- |
| Stage order, output directory, source preview                                    | `../m4a1.py`                                  |
| Shared seeded maps, grip checkering, receiver-only balanced albedo, finishes     | `materials.py`                                |
| Receivers, mechanism, RIS II, sights, furniture, magazines, markings and sockets | Corresponding named sections of `geometry.py` |
| Applied radii, original smart-project atlas and grip-panel UVs                   | End of `geometry.py`                          |
| Weapon/wrist/finger poses, events, shared review skins                           | `../m4_actions.py`                            |
| Clip selection, runtime sampling and explicit reset channels                     | `animations.py`                               |
| Mesh joining, native Actions export and read-only output assertions              | `export.py`                                   |
| Frozen review cameras, lights and color management                               | `studio.py`                                   |

Module imports do not build or mutate the scene. Geometry helpers remain local
to the assembly builder: their defaults refer to that build's materials/pivots.
There is no cross-weapon framework. Assembly order is intentionally retained to
preserve topology, triangulation, normals, primitive/material order and atlas UVs.
Do not replace this atlas with MCX's repeating planar projection: its left half
contains the original A2 checkering; other surfaces use the right half.

## Inputs and authority

Python owns the weapon geometry, surfaces, mechanisms, animation and exports.
Two existing, versioned shared inputs are explicitly retained:

- `assets/weapons/m4a1-block-ii/hand-reference.json`: wrist/finger calibration
  generated by `node tools/m4-hand-reference.mjs` from the shared runtime Arm
  calibration. Regenerate it only when intentionally changing that calibration;
  then rebuild the weapon. It is not inferred from an old weapon blend/GLB.
- `assets/player/arms/player-arms.blend`: shared appearance/bind data appended for
  excluded DCC review skins only. These skins/armatures are not in the M4 GLB.

Missing inputs fail rather than falling back to old generated weapon assets.
The adjacent asset README and photo/side-review JSONs document source limitations.
This migration does not redesign the approved original 2.2 mm rear aperture,
green post tip, trimmed support, balanced receiver finish, or handling contracts.

## Build (repository root, Blender 5.2.2)

```sh
blender -b -t 8 --python-exit-code 1 --python tools/blender/m4a1.py -- --quick
# Fresh scratch build, without changing the committed products:
blender -b -t 8 --python-exit-code 1 --python tools/blender/m4a1.py -- \
  --output /tmp/m4-authoring-review --quick
# Optional source renders only (requires a working GPU/color configuration):
blender -b -t 8 --python-exit-code 1 --python tools/blender/m4a1.py -- \
  --output /tmp/m4-authoring-review --quick --render
```

The command resets to an empty factory scene, creates four seeded 1024² maps,
builds named assemblies/pivots, applies radii and original atlas UVs, authors eight
clips and review arms, and saves an editable packed preview with Idle selected.
`--quick` affects only review resolution/samples. If the installed OCIO config is
incompatible, supply a compatible process-local `OCIO`; never disable color
management or alter the renderer/exposure to obtain a comparison.

The in-memory runtime copy then bakes the existing Bezier motion at **120 Hz**.
This is the historical runtime sampling lattice, not a new motion approximation.
Visibility is sampled on the same integer frames, authored CONSTANT, and exported
as STEP. Explicit TRS reset channels remain on every control in every clip.
Draw retains its held frame-75 endpoint value at its exact **74.4 frame / .620 s**
timestamp. The original sparse Bezier poses and shared review-arm actions remain
in the saved preview. Export curves are LINEAR for motion, without forced native
sampling; ordinary Blender Actions export merges matching NLA names. No code
reopens the output for writing. Post-export counts, interpolation and duration
assertions only read the result; the manifest is separate generated metadata.

## Review and validation

```sh
blender -b -t 8 assets/weapons/m4a1-block-ii/m4a1-block-ii.blend \
  --python-exit-code 1 --python tools/blender/m4_check.py
node tests/smoke/smoke-m4.mjs
npm test
npm run lint
npm run build
```

Use the existing gameplay/sight capture commands in the asset README when a GPU
lane is available. Do not weaken checks. For reproducibility, build into two empty
scratch directories in separate Blender processes; compare GLB/map/manifest
hashes against each other and the candidate. Blend metadata may contain output
paths; compare source geometry/materials/animation semantically, not file hashes.
For preservation, compare every geometry/index/UV/normal payload, all material
parameters and embedded map bytes, node/socket data, clip events, sampler times,
STEP transitions and fractional-time motion/hand targets. Quantify any numerical
exporter differences instead of introducing a blanket tolerance. Source renders
must use the same cameras, lights and valid view transform before/after.
